## New findings

| Severity | Finding | Reproduced behavior | Required correction |
| --- | --- | --- | --- |
| High | Excel's alternate date system is ignored | A synthetic `.xlsx` with `Workbook.WBProps.date1904=true` contains a formatted date of **2025-03-15**. Import returned HTTP 200 and persisted **2021-03-14**. The local parser returned the same wrong date. | Honor the workbook epoch when converting numeric date cells, or reject unsupported epochs before import. Test both date systems with actual serialized workbooks and database date assertions. |
| Medium | A failed import still creates suppliers | A company-specific trigger in the isolated test database rejected the final `IMPORT_LEDGER` audit insert. Import returned HTTP 400; the ledger transaction rolled back, but **one newly extracted supplier remained**. | Preallocate supplier IDs and commit new suppliers, ledger receipt, rows and audit together. A failed import should leave no new supplier records. Retrying must remain safe. |

`lib/parser.ts` converts every numeric date using the December 1899 epoch. `parseSheet` reads the workbook but does not pass its `date1904` setting into row/date conversion. Excel supports both epochs; the workbook metadata is documented by [SheetJS](https://docs.sheetjs.com/docs/csf/book/). The probe serialized and reopened the workbook, confirmed `date1904=true`, and independently formatted its date code as 2025-03-15 before testing the app. This is an observed date corruption, not a claim that the supplied client workbook uses this epoch.

`app/api/upload-gl/import/route.ts` inserts suppliers in its extraction loop before the final database batch containing the ledger receipt, financial rows and audit. The failure does not leave ledger rows, and the returned error correctly says no transaction rows were saved. It nevertheless leaves an unaudited supplier side effect. No incorrect tax batch was generated by this probe; the wrongly dated row falls outside the supported calculation window.
